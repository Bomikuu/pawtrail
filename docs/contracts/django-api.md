# Proposed Django API contract

Achievements add authenticated `GET /me/achievements`, `POST /me/achievements/claim`, `PATCH /me/achievements/showcase`, `POST /me/achievements/activity`, `GET/POST /me/achievement-proofs`, and moderator-only `GET /moderation/achievement-proofs` plus `POST /moderation/achievement-proofs/:id/review`. Shapes are in `features/achievements/schemas.ts`. Rewards are server-derived and atomically idempotent; review is independent/versioned. Immutable Kibble entries additionally support `achievement_awarded` and `achievement_reversed`. Public profiles optionally expose consented aggregate `mastery`; existing `badges` contain only selected active awards. No proof documents, private application data or activity references belong in public responses. Matching Django implementation/conformance remains external.

Profile avatars: the existing `avatar_id` accepts the reserved curated IDs `pawtrail-avatar-01` through `pawtrail-avatar-30`. The backend resolves them from the fixed PawTrail catalog into public image DTOs; it must not accept caller-supplied URLs as curated assets. Other media IDs retain owner/publication checks. Profile responses return the selected image; session actors and visible post/comment author projections may include the same optional `avatar` image. Hidden contribution identities return no identifying image. Live backend conformance remains unverified.

Status: proposed backend contract with a frontend adapter implementation; no live conformance is claimed. Test-authoring/execution steps were skipped by explicit user instruction. The [specification](../superpowers/specs/2026-11-02-pawtrail-design.md) owns domain signatures and privacy/state invariants.

## Transport rules

Browser requests use same-origin `/api/v1`. Server Components call the selected service directly. In real mode only the server adapter calls `DJANGO_API_BASE_URL`, which includes the upstream API prefix; append resource paths once. Never forward tokens to a caller-controlled host or follow pagination URLs to a different origin.

Domain methods return promises. JSON uses camelCase inside the frontend; I1 maps Django snake_case fields explicitly. Lists normalize to `{ items, count, nextCursor }`. Upstream `{ count, next, previous, results }` is normalized without dropping pages. Errors normalize to `{ code, message, status, fieldErrors?, requestId? }`. Cross-owner reads of sensitive resources return 404; forbidden actions on otherwise public records return 403; validation is 400/422; version/idempotency conflicts are 409. Domain response bodies pass Zod validation.

All POST create/submit/approve/support commands support `Idempotency-Key` where repeated delivery can duplicate a side effect. The server persists the actor+operation+key+payload hash and original result. Same key plus different payload is 409. Set-style PUT actions express desired state and are naturally idempotent. Versioned review/edit commands carry `expectedVersion`; do not silently accept stale overwrites. Pagination is default 12/max 50 with stable timestamp/ID ordering and opaque cursors.

Session cookies are HttpOnly with Secure in production, appropriate SameSite, expiry, rotation/logout and server-side credential protection. Validate same-origin/CSRF for mutations. The Django service must enforce object/organization permissions, filter visibility, own exact location policy and private media delivery, process immutable ledger/evidence review transitions, and emit consistent public DTOs. Client route guards alone are insufficient.

## Required contract examples at I1

I1 adds executable fixtures for list/detail/create, field validation, 401/403/404/409, expired session/refresh failure, idempotency replay/payload conflict, pending-vs-public visibility, canceled request, missing cursor page, malformed success and private media authorization. The same domain suite runs against mock storage and controlled Django HTTP fixtures. Fixed errors/retries may not silently fabricate real records or payments.

The actual Django backend, durable production storage, provider tokens, geospatial indexes, review operations, external notifications and payment processing remain separate delivery work. A configured live environment is required before claiming live backend conformance.

## Native implementation extensions

The owner changed execution to direct implementation with no agents or automated testing. `GET /me/profile` supplies the current private profile for editing. Animals and sightings accept an explicit owner scope; events accept a current-user scope. Animal edits support care/adoption status and current versions. Animal verification evidence is attached through report/edit input, separately from public photos. Private shelter evidence uses an explicit verification target in the upload input, current organization permission, and the independent moderator queue.

Campaigns support an optional Horde beneficiary, itemized estimated budget and timeline. Budget estimates remain separate from expenses. Expenses accept private receipt IDs; the owner/organization fundraising dashboard includes their authorized associations. Public expense DTOs never include receipt IDs. Photo updates use linked pending community publications and appear publicly only while that publication remains approved. Original financial history stays append-only; corrections supersede without deleting.

Adoption application detail includes private versioned status history. Event detail includes only the current viewer's attendance flag. Reward reversal is a negative immutable Kibble entry. Ranking uses net earned points, approved contribution count and stable user ID. Public level advances once per 100 net earned Kibble, starting at one; Helping Paw requires approved mission participation.

Login/registration returns `{access, refresh, session}`; the session uses the sanitized frontend shape. Refresh returns `{access, refresh?}`. Tokens are sealed in an HttpOnly same-origin cookie by the BFF and stripped from browser JSON. See `../backend-integration.md` for configuration and production limitations. No automated or live backend conformance run was performed.

### Public recognition board

`GET /leaderboard` supports `period=all|month|week`, `category=all|missions|sightings|fundraisers`, optional `q` (name or username), `cursor`, and `limit` (maximum 50). The response extends the ordinary page with `podium` (top three of the selected category/period, unaffected by name search), `summary` (`active_helpers`, `kibble_earned`, `contributions`, `animals_helped`), `offset`, and `previous_cursor`. Each entry includes `avatar`, `level`, `contributions` (`missions`, `sightings`, `fundraisers`), chosen `badges`, and opt-in `mastery`, alongside identity, rank, Kibble and provenance. These fields are required by the extended schema; an older backend response fails validation instead of inventing zero activity. No live Django conformance has been established.

The public projection excludes undiscoverable/contribution-private members and anonymous campaign support. Mission counts require an independent approval and a public mission. New participation reviews persist nullable `reviewed_at`; legacy mission awards provide an approval-date fallback. Undated legacy approvals count only in All time. Time windows use Manila (Monday-start week). Corrections affect their recorded period; each member's ranking Kibble is floored at zero. Category views rank by their matching count; all contributions ranks by net Kibble. Ties use approved mission count, then stable account ID. Summary totals cover the selected period across consenting members before category/name filters. `animals_helped` counts distinct public animals linked to approved missions, without asserting rescues or adoption outcomes. See `docs/implementation/leaderboard.md`.

Public profiles and the `author` object on post/comment views may include `leaderboard_rank`, nullable and restricted to integers 1–10. It is the member's current **all-time, all-contributions** rank, using the same eligibility, points and tie-break policy as `/leaderboard?period=all&category=all`; it is not a permanent historical badge. Non-qualifying or contribution-private identities return null. The browser renders the crown only for attributed identities. Missing fields from older responses default to null rather than inventing recognition; profile, post and comment write inputs do not accept this derived field.

### Profile covers and overview activity

Public/private user DTOs add `banner_id` (`meadow`, `garden`, `coast`, `starlight`, `sunset`, `explorer`, `home`, `champion`), defaulting to `meadow` for older responses. Profile update accepts an optional `banner_id`; omission preserves the stored choice, and unknown preset IDs/URLs fail validation. Preset URLs and focal positions are resolved by the application, never accepted from profile inputs.

Public profile detail adds nullable `impact` (`kibble_earned`, `events_joined`, `membership_days`, `level_progress`) and nullable `activities`: public records with `id`, `kind=sighting|mission|fundraiser`, `title`, `description`, `href`, `created_at`. Omitted legacy fields default to null (unavailable), never fabricated counters. `level_progress` is net lifetime Kibble modulo 100; `level` is one plus its integer quotient. Event totals count distinct RSVPs to visible, non-cancelled events and do not assert attendance; membership days are elapsed time, not active days. `summary.donations` now counts distinct publicly supported campaigns to match the Fundraisers supported label. Mission attribution requires independent approval; private proof text and media are excluded. Privacy opt-out returns null impact, no activity entries, no badges and no animal associations. The local mock/BFF implements this contract; live Django conformance remains unverified.

### Pet activity profiles

`GET /animals/:slug/activity` / `animals.activity(slug, query)` supports `kind=all|sightings|help|tagged`, `sort=priority|newest`, optional public-text `q`, `cursor`, and `limit` (maximum 50). Response extends the page envelope with `summary` (`tagged_posts`, `sightings`, `helpers`, `followers`, `open_missions`, `active_fundraisers`), `photos` (unique public image, originating `href`, public credit), and nullable `latest_sighting` (`observed_at`, generalized `location`).

Items have `kind=sighting|mission|care|fundraiser|post`, prefixed stable `id`, timestamp, priority, label/title/public text, destination, privacy-projected human `author`, approved public media, optional approximate location, provenance and nullable embedded `post`. Help filter includes independently approved care and tagged help/feeding/rescue stories; sightings filter contains actual published sighting records. The current animal tag is first in its own tagged-story presentation. Pet identities cannot supply post authors. Counters and photos cover all eligible records before paging/filtering; private people do not contribute identities to helper/follower totals. Source media must be approved for public-image use; evidence/media-preview records are excluded.

Priority order: open, unexpired missions and active fundraisers (0), published sightings/independent care completions/tagged care stories (1), closed or expired help (2), other tagged stories (3), newest timestamp within each group, stable ID last. `newest` ignores priority. Cursors are bound to animal, viewer, query, filter and sort. Animal profile DTO adds allowlisted `banner_id` defaulting to `meadow` and current-viewer `viewer_can_manage` defaulting false; this flag is not a write input and does not expose owner IDs. Animal report/update accepts optional `banner_id` through the existing review/version policy. Local mock and BFF implement these additions; live Django conformance has not been verified.
